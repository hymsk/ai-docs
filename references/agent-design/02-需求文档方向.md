## 1. 背景与问题定义

需求文档（PRD / SRS / 用户故事 / 验收标准等）是软件开发中最关键的制品之一，但人工编写成本高，且容易出现遗漏、歧义和误解。LLM 与 Agent 技术为需求文档生成带来了自动化机会，但直接让 LLM"一次性"生成完整需求文档存在明显缺陷：

- **幻觉**：编造不存在的功能或约束；
- **信息缺失**：原始输入往往欠规格化（underspecified），隐含需求无法凭空补全；
- **结构混乱**：单次生成难以将需求正确归入 SRS 的对应章节；
- **不可验收**："优化体验""提升性能"等表述无法转化为测试。

本报告总结学术界与工业界的最新实践（2025–2026），回答：**如何设计 Agent 系统，使其生成的需求文档更完整、更一致、可追溯、可验收。**

## 2. 核心研究发现

### 2.1 澄清先于生成：从"Chat"走向"Interview"

**这是本次调研中最重要的结论。**

日本一项工业实证研究（ACM WSSE 2025）用 ChatGPT-4o 对真实商业系统做了三组对照实验：

| 方法 | 方式 | 结果 |
| --- | --- | --- |
| 方法 1 | 单条 prompt 批量投喂系统概述 | 功能列表可用，ER 图缺失 |
| 方法 2 | **交互式对话**，AI 作为资深工程师顾问主动提问，分批提供信息 | **综合效果最佳**，成功生成 ER 图及功能/屏幕/API 清单 |
| 方法 3 | 先获取建议再批量生成 | 介于两者之间 |

关键数据：仅 ER 图一项，人工约需 120 分钟，AI 辅助仅需几分钟，**工时降低约 95%**。

学术侧进一步验证了"访谈式"的价值：

- **OntoAgent**（arXiv 2605.05828）：用"经验本体论（Experience Ontology）"指导访谈式需求启发，对自由聊天式基线实现 **隐含需求覆盖率（IRE）提升 33%**、**关键问题效率（TKQR）提升 21%**。其流程为 ParseUser → ScoreOnto → ReRankOnto → GatePrune → QuestionGen 的迭代决策循环。
- **语音访谈 Agent 原型**（ICSE 2026 AGENT Workshop）：GPT-4o-mini 驱动的访谈 agent 平均覆盖 77.5% 相关需求，用户可用性评分 4.0/5。

**启示**：好的需求生成 Agent 不是"接收指令→输出文档"，而是"分析输入缺口→有策略地提问→逐步收敛→再产出文档"。提问应分组进行（如用户角色与流程 / 功能边界 / 非功能性需求 / 边界情况与风险），一次只问一个主题下的问题。

### 2.2 任务分解：不要一步到位生成整份文档

**ReqInOne**（arXiv 2508.09648）证明：单步 prompt 直接生成完整 SRS 会显著产生幻觉和错位；将任务分解为三个专职子任务后，质量超过基线方法甚至初级需求工程师：

1. **Summary Task**：填充引言、干系人、用例、术语表等概要章节；
2. **Requirement Extraction Task**：按 INCOSE 标准句式抽取需求——"The \<subject\> shall \<action\> \<object\>, when \<condition\>"；
3. **Requirement Classification Task**：将需求分类为 FR/NFR 及 NFR 的 11 种子类型（可用性、安全性、可维护性等），配合关键词指标词（indicator terms）+ few-shot 示例提升准确率。

其他系统的分解方式佐证了这一模式：

- **KGMAF**（ASE 2025）：六个角色化 Agent 协作——Interviewer、End-User、Analyst、Archivist、Reviewer、Deployer，共享一个"制品池（artifact pool）"作为通信媒介（黑板架构）；
- **automated-SRS-generator**（LangGraph）：五阶段流水线——Ingestion → Elicitation（逐题 interrupt）→ Drafting（**6 个章节并行撰写**）→ Diagrams（Mermaid 图）→ Finalization；
- **Goal2Story**：基于 Impact Mapping 的多 Agent 编队，即使使用小型私有 sLLM 也优于单个强模型 Super-Agent（FHR 达 77.93%，QuACE 达 97%）——**框架化的任务分解比堆模型能力更有效**。

### 2.3 结构化模板与书写规范是质量的地基

- **标准模板**：IEEE Std 830 / ISO/IEC/IEEE 29148:2018 是最常用的 SRS 骨架；PRD 则普遍采用"背景与问题 → 目标与成功指标 → 用户与场景 → 功能需求（用户故事 + 优先级 P0/P1/P2）→ 范围与边界（In/Out of scope）→ 验收标准 → 依赖与约束"结构。
- **强制结构化输出**：主流实现均通过 JSON Schema / Pydantic `with_structured_output` 强约束模型输出，失败时降温度重试（如 2 次重试递减 temperature）。
- **需求书写规范**（可直接写入 Agent 的 Skill/规则文件）：
  - 用户故事格式：作为 [角色]，我希望 [能力]，以便 [价值]；一条故事只描述一个可交付能力；
  - 验收标准格式：Given-When-Then 或"当…时，应…"，每条需求至少一条可验证条件；
  - **禁用词替换**：「优化体验」→「首屏加载 < 2s」；「尽量」「视情况」→ 明确规则或列出例外；
  - 缺项统一占位 `[请补充：xxx]`，禁止模型自行编造。

### 2.4 知识注入：领域知识决定专业度

KGMAF 的核心贡献是证明"裸 LLM + 提示词"不够，需向不同角色 Agent 注入三类来源的知识：

1. **现有软件项目**：常见需求制品类型及其依赖关系（如 IR→SRL→SRS）；
2. **RE 文献与标准**：IEEE 830 / ISO 29148 的模板、分类法、质量度量、验证准则；
3. **领域专家**：通过认知启发法捕获专家的抽象、排序、冲突消解策略。

知识按六大类注入：Elicitation / Analysis / Specification / Validation / Contextual / Cognitive Strategies。OntoAgent 的经验本体则从同域历史需求文本中自动归纳出高频"需求关注点"，作为提问的检查清单。

### 2.5 可追溯性：对抗幻觉的关键手段

ReqInOne 在抽取每条需求时强制附加两个字段：

- **Trace to Source**：该需求的原文出处；
- **Reason**：为什么抽取它。

这种"先给证据再给结论"的约束显著抑制了无中生有的需求，同时建立了 SRS 内部的追踪链路。SuPReA 同样采用"校验失败自动重查（re-querying）+ 更严格格式指令"的反馈环来补偿 LLM 已知缺陷。

### 2.6 人机协同（HITL）与迭代闭环

所有高质量系统都不是全自动黑盒：

- **HITL 中断点**：automated-SRS-generator 在每组启发问题后 `interrupt()` 等待用户确认；KGMAF 在关键制品上设置人工审查关卡；实验表明偶发的冗余与冲突正是在这些关卡被修正；
- **局部再生成**：SuPReA 支持"只重新生成某个 artifact 而不动其余"，适配敏捷迭代；automated-SRS-generator 支持单章节定向修订模式；
- **澄清闭环**：开源项目 spec-agent 提出"澄清 → 更新 → 校验"循环，把澄清记录沉淀为 `00-clarifications.md`，随文档集持续演化；
- **自检提示**：Addy Osmani 建议 prompt 中显式要求"完成后对照规格核对，列出未覆盖项"，并引入三层边界（Always / Ask first / Never）约束 Agent 行为。

### 2.7 上下文管理：警惕"指令诅咒"

研究表明（curse of instructions）：prompt 中规则越多，模型对每条规则的遵循度越低。对策：

- 大规格拆分为独立文件/章节，每次只喂当前任务相关切片；
- 让 Agent 先生成"扩展目录 + 每节摘要"，摘要常驻上下文，细节按需加载；
- 多 Agent 场景下各 Agent 只持有自己职责范围内的知识切片。

## 3. 推荐参考架构

综合上述发现，一个高质量的需求文档生成 Agent 建议采用如下流水线：

```
┌─────────────────────────────────────────────────────────────┐
│  Phase 1  摄取（Ingestion）                                  │
│    解析原始输入 → 提取标题/领域/角色/流程/约束/实体            │
├─────────────────────────────────────────────────────────────┤
│  Phase 2  启发（Eliciting）★ 决定质量上限                     │
│    对照知识库/本体识别信息缺口                                │
│    分组提问（一次一题，HITL 中断）                             │
│    记录澄清日志 clarifications.md                            │
├─────────────────────────────────────────────────────────────┤
│  Phase 3  起草（Drafting）                                   │
│    摘要任务 → 填充概要章节                                    │
│    需求抽取（INCOSE 句式 + Trace-to-Source + Reason）         │
│    FR/NFR 分类（含 NFR 子类型）                               │
│    各章节并行撰写（结构化 JSON 输出 + 校验重试）               │
├─────────────────────────────────────────────────────────────┤
│  Phase 4  审查（Review）                                     │
│    Reviewer Agent 对照模板做符合性检查                        │
│    （缺节 / 不可验收表述 / 成功指标是否可衡量）                │
│    一致性校验：跨章节冲突检测                                 │
├─────────────────────────────────────────────────────────────┤
│  Phase 5  定稿（Finalization）                               │
│    组装 Markdown/DOCX、Mermaid 图（用例图/类图/ER图/活动图）   │
│    支持单章节定向修订，版本留痕                                │
└─────────────────────────────────────────────────────────────┘
```

**工程要点清单：**

1. 每个 LLM 节点绑定 Pydantic/JSON Schema，失败降温度重试；
2. 提问必须分组且有优先级排序（先问影响范围大的）；
3. 所有需求带 ID（R1/R2…）、优先级、来源追溯；
4. 模板与书写规范固化为 Skill/规则文件（SKILL.md + reference.md），随仓库提交保证团队一致；
5. 简单任务从简——规格详细程度应与任务复杂度匹配，避免对 trivial 任务过度工程化。

## 4. 评估指标体系

| 维度 | 指标 | 出处 |
| --- | --- | --- |
| 文档整体质量 | 内部一致性、非冗余性、完整性、简洁性、可追溯性（Likert 1–5） | ReqInOne |
| 单条需求质量 | 无歧义、可理解、正确性、可验证、合规性（Likert 1–5） | ReqInOne |
| 启发有效性 | 隐含需求覆盖率 IRE | ReqElicitGym / OntoAgent |
| 提问效率 | 回合折算关键问题率 TKQR | OntoAgent |
| 内容真实性 | 事实命中率 FHR | Goal2Story |
| 综合质量 | QuACE（语法/语义/语用/一致性四维） | Goal2Story |
| 分类准确性 | Precision / Recall / F1（对照 PROMISE、PURE 数据集） | ReqInOne |

## 5. 结论

1. **访谈式 > 投喂式**：让 Agent 主动、有策略地澄清，是提升需求文档质量的第一杠杆（工业实验与多项研究一致证实）；
2. **分解 > 一步到位**：摄取→启发→抽取→分类→起草→审查的分阶段流水线显著优于单 prompt 生成；
3. **模板 + 规范 + 结构化输出**是质量地基，标准句式与禁用词规则直接决定需求是否可验收；
4. **知识注入与可追溯性**分别解决"专业度"与"幻觉"两大痛点；
5. **人机协同不是妥协而是必要**：HITL 中断点、局部再生成、澄清闭环构成可持续迭代的文档资产；
6. 评估应从"看起来不错"转向量化指标（IRE / FHR / QuACE / Likert 五维）。

一句话总结：**好的需求生成 Agent = 访谈式澄清 + 流水线分解 + 强制结构与溯源 + 知识注入 + 人在回路的迭代闭环。**
