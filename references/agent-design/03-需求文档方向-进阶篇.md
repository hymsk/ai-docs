## 1. 深度专题一：歧义与冲突——需求质量的核心敌人

### 1.1 为什么必须优先治理歧义（量化的下游代价）

**Orchid 基准**（arXiv 2604.21505）首次系统量化了需求歧义对下游的影响：

- 构建 1,304 个含歧义的任务（覆盖**词汇、句法、语义、模糊性**四类歧义）；
- 歧义需求使 GPT-4 代码生成性能下降超过 **30%**；
- 歧义使模型的"功能分歧率"近乎翻倍（GPT-4 从 14.09% 升至 28.29%）——同一份歧义需求，多次生成会得到互相不兼容的实现；
- 关键短板：LLM **能检测**歧义（召回尚可）但**无法精确定位**歧义来源并给出有效消解（定位率仅约 8–21%，且精确率仅约 50%，大量误报）。

**启示**：生成侧 Agent 必须内置"歧义感知"机制，不能指望通用 LLM 自发解决；检测出歧义后应转交人工或澄清流程，而非让模型自行其是。

### 1.2 语用歧义的 RAG 检测方案（多级知识库模拟干系人）

arXiv 2607.04436 提出了一种巧妙的检测思路：

1. 为每条需求生成**启发问题（Elicitation Questions, EQs）**，锁定潜在歧义术语；
2. 构建四类知识库：规格书自身（KRK）+ 新手/中级/专家三级领域库（KNK/KIK/KEK，可用 WikiDoMiner 从 Wikipedia 自动构建）；
3. 用需求+EQ 分别查询三个级别知识库，检索结果两两计算余弦相似度（27 种组合）；
4. 任一组合相似度全部超过阈值 T → 无歧义；否则标记为语用歧义；
5. 消解阶段用专家知识库生成候选改写，**最终必须由需求分析师确认**。

实测：GPT-4o-mini 检测宏平均召回 0.75；Mistral-7B 生成的消解文本在清晰度与一致性上得分最高。

### 1.3 冲突检测的三条技术路线

| 路线 | 代表工作 | 特点 |
| --- | --- | --- |
| 判别式小模型 | TSRCDF-SS（PLOS One 2026）：SBERT+SimCSE 双编码器 + 六元拼接 + Focal Loss 变体混合损失 + 迁移学习 | 同域 macro-F1 提升 4.9–12.1%；跨域仍受冲突样本稀缺制约 |
| LLM few-shot | AraREQ（LREC 2026）：27K 需求对数据集 + 端到端检测/消解系统 | few-shot 显著改善少数类（冲突类）识别 |
| 结构化表示 + LLM | IDRAAK（arXiv 2608.08801）：语义需求表示 SRR（数值约束/极性/模态等字段级证据） | 可解释、可审计，适合安全关键场景 |

### 1.4 重要反直觉发现：Agent 复杂度 ≠ 效果

IDRAAK 在 890 个合成扰动样本上对比了六种工作流：

- **8 个专职 Agent 的完整多智能体流水线**（翻译→抽取→对齐→漂移检测→证据→批评家→校准→裁决）；
- 单次 LLM 调用 + 6 个 few-shot 示例的**直接判定**。

结果：简单方案 MCC=0.888 / F1=0.983，**全面优于**多智能体方案（结构化单 agent MCC=0.501，确定性基线 MCC=0.474）。论文明确结论："增加 agentic 复杂度并不必然提升检测效果"。另外：LLM 原始置信度校准很差（ECE 最高 0.464），Platt scaling 校准后降至 <0.02——若用置信度路由人工复核，必须先做后验校准。

**启示**：需求文档 Agent 的每个环节都应从"最简单的有效方案"起步，用评测驱动决定是否引入多 Agent。

## 2. 深度专题二：知识注入选型——RAG 是主力，微调是补丁

### 2.1 RAG 与微调的对比结论

arXiv 2312.05934 的对照实验表明：**在知识注入任务上 RAG 稳定优于无监督微调**（无论新旧知识）；微调不稳定且存在灾难性遗忘风险；微调+RAG 组合反而可能不如纯 RAG。若坚持微调，同一事实需要多种改写形式反复曝光才有效。对需求 Agent 的含义：领域规范、历史需求、术语库应走 RAG 路线，不要指望微调让模型"记住"业务知识。

### 2.2 工业级参考架构（汽车制造业实证）

arXiv 2603.20534 在 669 条真实需求 + 四个企业标准上的生产级评估给出了可复用的组件贡献度：

| 组件 | 贡献 |
| --- | --- |
| **混合检索**（BM25 + 语义向量 + RRF 融合 + 交叉编码器重排） | MRR 0.683 → 0.847（+24%），贡献最大 |
| **领域自适应嵌入**（在 15,127 条本域需求上对比学习微调 sentence-transformer） | MRR 再 +6.7%，准确率 +2.1% |
| **多供应商 LLM 编排**（按任务路由到不同模型） | 成本降低 47%，质量不降 |
| **溯源元数据**（文档版本/章节路径/页码/检索分数/生成元数据） | 不影响准确率，但专家信任度达 4.67/5——合规场景（ISO 26262 等）必备 |

整体效果：抽取准确率 98.2%（超 BERT 基线 24.4%、超无接地 LLM 19.6%），人工分析时间减少 83%。

### 2.3 Graph-RAG 用于追溯性与合规检查

arXiv 2412.08593 将高层法规/组织需求构建为知识图谱（实体-关系抽取 + 迭代 gleanings），SRS 条目作为查询检索关联条款，配合 CoT/ToT 提示做违规判定。Graph-RAG + ToT 组合效果最佳，适合"需求 ↔ 上位规范"的交叉引用类推理；但图构建成本高、依赖输入数据完整性。

### 2.4 别忘了"RAG 系统本身也需要需求工程"

arXiv 2505.07553 的海事案例研究指出：知识库要求**多样性重于数量**；"检索需求"只能通过上线观察用户真实使用来迭代发现；应为用户提供过滤器等补偿机制弥补知识缺口。这对"用 Agent 生成需求"同样成立：知识库建设本身要当作一个持续运营的需求工程过程。

## 3. 深度专题三：Agent 框架选型（2026 年格局）

### 3.1 三种执行模型

| 模型 | 代表框架 | 适用 |
| --- | --- | --- |
| **Graph（显式状态图）** | LangGraph、Google ADK workflow agents | 需要确定性控制流、可审计、人在回路 |
| **Crew（角色分工）** | CrewAI | 快速原型、角色清晰的团队协作隐喻 |
| **Handoff（控制权移交）** | OpenAI Agents SDK | OpenAI 生态、客服式路由 |

AutoGen 已并入 Microsoft Agent Framework（GA 2026），成为 Azure/.NET 生态选项。

### 3.2 横向对比要点

| 维度 | LangGraph | CrewAI | OpenAI SDK | MS Agent Framework | Google ADK |
| --- | --- | --- | --- | --- | --- |
| 生产成熟度 | 高（checkpointing/time-travel/HITL interrupt 内置） | 中（无内置检查点） | 高（tracing/guardrails 内置） | 中高 | 高（限 GCP 内） |
| 模型灵活性 | 全部供应商 | 全部（LiteLLM） | 仅 OpenAI 原生 | 模型灵活 | Gemini 原生 |
| 可观测性 | LangSmith | 较弱 | 内置 | 云原生 | 云原生 |
| MCP 支持 | 手动封装 | 插件 | 原生 | 部分 | 部分 |
| 学习曲线 | 中陡 | 最低 | 低 | 中 | 中 |

### 3.3 对需求文档生成场景的建议

需求生成工作流的特征是：**长时序、有状态、多个人工确认点（HITL）、需审计留痕**——这正是 Graph 模型的靶场。因此：

- **首选 LangGraph**：`interrupt()` 原生支持逐题澄清中断；checkpoint 支持暂停/回放（对应"局部再生成"需求）；automated-SRS-generator 已验证此路线可行。
- 快速验证原型期可用 CrewAI（角色映射自然：Interviewer/Analyst/Reviewer），但注意社区基准显示其 token 开销偏高，且生产化需自建状态持久化。
- 通用忠告（多篇评测一致）：**先做单 Agent + 工具，用测量证明瓶颈后再拆分多 Agent**；框架选择是可逆决策（MCP 保证工具可移植、A2A 保证互操作），把精力投入在架构与评测而非框架之争。

## 4. 深度专题四：需求制品的自动化质量评估（生成后的守门员）

### 4.1 用户故事：规则工具与 LLM 各有所长 → Dual-gate 混合策略

Springer 2026 扩展对比研究（AQUSA vs GPT-5/GPT-5-mini/GPT-4，182 条工业用户故事）：

- AQUSA（基于 QUS 框架的规则工具）：精确率最高（0.61），擅长句法缺陷（缺角色、非原子、格式不统一），但无法发现语境问题；
- GPT-5-mini：召回最高（0.81）、F1 最高（0.62），能抓住"A as a Mike"这类语义异常（人名≠干系人角色），但前沿模型 GPT-5 幻觉率高（85 个误报）、过度泛化；GPT-4 过度保守漏检严重；
- 结论：**两者单独都不够 → "双闸门"策略**：先用 AQUSA 做结构性校验（确定、可复现），再用轻量 LLM 做语境精修（语用/语义）。

QUS 框架的 13 条准则（句法/语义/语用三维）可直接用作生成侧 prompt 的自检清单：well-formed、atomic、minimal、conceptually sound、problem-oriented、unambiguous、full sentence、estimatable、unique、conflict-free、uniform、independent、complete。

### 4.2 验收标准（Gherkin）自动生成

SEET 2026 研究：按 Epic 组织的 JSON 约束流水线（Timeless）vs 直接零样本生成：

- 结构有效率 100%（JSON schema 约束）vs 99%（零样本）；
- 语义需求覆盖率 TF-IDF 词面指标会低估（94.3% vs 92.9%，差距不大），但**专家盲评显著偏好 epic 组织版**：正确性 4.61 vs 4.14、可执行性 4.61 vs 4.07、完整性 4.31 vs 3.50；
- 启示：验收标准的组织粒度和上下文供给比裸生成更重要；评估覆盖率要用嵌入相似度而非词面重叠。

### 4.3 LLM 当评审员的稳定性

早期研究已提示：ChatGPT 做用户故事质量评判时，三次运行完全一致的场合与人类一致率约 75%；采用"三次投票取二"可提高一致性。工程上：评审 Agent 应固定温度=0、多次采样投票、并与规则工具交叉验证。

## 5. 深度专题五：商业产品与开源 Skill 实践扫描

### 5.1 海外 PM Agent 市场（2026）

市场呈碎片化细分而非整合：

| 产品 | 定位 | 关键事实 |
| --- | --- | --- |
| ChatPRD | PRD 文档生成 + CPO 级 coaching | 号称 10 万+ PM、75 万+ 文档；$15–29/mo；SOC 2 Type II；承诺不用客户数据训练 |
| BrainGrid | 给 AI 编码工具消费的 spec | Menlo 领投 $1M pre-seed（2026.03）；MCP 集成 |
| Modem | Slack/Discord/GitHub 反馈聚合成上下文图谱 | Accel 投 $4.4M |
| BuildBetter | 企业级客户情报 → PRD/ticket | Brex、PostHog、汉莎客户 |
| Korey | 工作流编排 + 安全 | 与 Anthropic 零数据保留协议，企业安全标杆 |
| Product Manager Skills | 开源：49 个 PM skill + 6 个命令工作流 | 四个月 5K+ star，把 Claude Code 变成免费 PM agent |

值得注意的行业信号：几乎所有产品的独立第三方评测极少，厂商口径主导——选型务必 POC 验证。

### 5.2 国内工具

- **PingCode**：私有化部署/信创适配是核心卖点，AI 建议"弹窗呈现、人来执行"的可控交互模式被实践者认可；
- **墨刀 AI Agent**："文档即原型"——PRD 直接转高保真可交互原型，弥合需求与设计断层；
- Notion AI / Jira+插件：AI 强但需求管理工作流弱，适合轻量场景。

### 5.3 开源 PRD Skills 的五种设计流派（对自研 Agent 有直接借鉴意义）

| 流派 | 代表 | 设计哲学 | 适用 |
| --- | --- | --- | --- |
| Discovery-first | GitHub awesome-copilot `prd`（17.5K 安装） | 动笔前必问三件事（痛点/成功度量/约束），明令"不要假设上下文"，输出 Strict PRD Schema | 模糊想法需要澄清 |
| Context-direct | Matt Pocock `to-prd` | 不提问，探索代码库后直接转化，打 `ready-for-agent` 标签 | 工程师已知做什么，只需格式化 |
| Enterprise-template | `prd-generator` | 13 模块全模板 + 标准/精简/一页纸/技术/设计五种变体 + AARRR/HEART/OKR 指标框架 + validate_prd.sh 自动查缺脚本 | 大型企业立项交付 |
| Principle-based | `writing-prds` | 不给模板给思想：Lead with why、PR/FAQ 强迫清晰、Demos before memos（11 位顶级 PM 洞察） | 提升底层写作能力 |
| Hard-gate brainstorm | `brainstorming` | HARD-GATE 规则禁止未确认方案就动笔；每次只问一个问题；确认后出 2–3 方案供选择 | 非专业人士、新手友好 |

共同模式提炼：**① 先澄清后撰写是主流共识（5 个中 3 个强制前置提问）；② Schema/脚本化校验保证下限；③ 分场景模板变体避免一刀切；④ 把"完成定义"写进流程闸门。**

## 6. 修订版推荐架构（v2）

在第一篇五阶段流水线基础上叠加三层能力：

```
┌──────────────────────────────────────────────────────────────┐
│ 知识层（新增）                                                │
│  · 混合检索：BM25 + 领域微调 embedding + RRF + 交叉编码器重排   │
│  · 规范库(ISO 29148/QUS) + 历史 PRD 库 + 术语/本体库           │
│  · 全链路溯源元数据（版本/章节/页码/分数）                      │
├──────────────────────────────────────────────────────────────┤
│ 编排层                                                        │
│  · 框架：LangGraph（HITL interrupt + checkpoint + 回放）       │
│  · 从单 Agent 起步；仅当测量证明瓶颈才拆分角色                  │
│  · 每个 LLM 节点：结构化输出 + 失败降温度重试                   │
│    置信度经 Platt 校准后再用于人工复核路由                      │
├──────────────────────────────────────────────────────────────┤
│ 质量守门层（新增，Dual-gate 双闸门）                           │
│  第一道（规则）：AQUSA 类结构校验 + 必填节/禁用词脚本检查        │
│  第二道（LLM）：轻量模型做语用/语义审查，多次采样投票            │
│  第三道（专项）：歧义检测（EQ + 多级知识库比对）                │
│              冲突检测（成对一致性）                            │
│              合规追溯（Graph-RAG 对照上位规范，可选）           │
│  未通过 → 回到澄清循环，记录 clarifications                    │
└──────────────────────────────────────────────────────────────┘
```

落地顺序建议：
1. **Week 1–2**：单 Agent + PRD 模板 Skill + 结构化输出 + validate 脚本（对标 prd-generator 流派）；
2. **Week 3–4**：接入访谈式澄清（分组提问 + 中断），固化为 HARD-GATE 规则；
3. **Month 2**：建混合检索知识层与溯源元数据；接入 QUS/AQUSA 双闸门评审；
4. **Month 3+**：按评测数据决定是否引入多角色协作、Graph-RAG 合规检查、领域 embedding 微调。

## 7. 风险与开放问题

1. **过度自动化风险**：Orchid 证明 LLM 无法自主定位/消解歧义——凡涉及歧义消解与冲突仲裁，人工确认不可省略；
2. **评测数据稀缺**：冲突/歧义标注数据集少且类别极不平衡（AraREQ 中冲突对仅占约 2%），跨域泛化仍是未解难题；
3. **厂商口径可信度低**：PM Agent 市场几乎无独立评测，采购决策必须 POC；
4. **成本结构**：Graph-RAG 图构建、多 Agent 编排、交叉编码器重排都有实打实的成本，需像工业 RAG 论文那样做多供应商路由与组件消融，把钱花在贡献最大的组件上；
5. **中文/多语言缺口**：现有基准以英文为主（PURE/PROMISE），AraREQ 类工作刚起步；中文需求语料与评测集是空白机会。

## 8. 进阶篇核心结论

1. **歧义是第一敌人且有量化代价**（下游性能 -30%、实现分歧率翻倍），但 LLM 只会"发现"不会"定位消解"——必须由澄清流程和人工闭环兜底；
2. **简单方案常常更强**：few-shot 单次调用击败 8-Agent 流水线；每个环节从最简方案起步、评测驱动加复杂度；
3. **知识注入选 RAG 不选微调**：混合检索贡献最大（+24% MRR），领域微调 embedding 是第二杠杆（+6.7%），溯源元数据买不来准确率但买得来信任与合规；
4. **质量守门用双闸门**：规则工具管结构与下限（AQUSA 精确率高），轻量 LLM 管语境与上限（召回 0.81），各补其短；
5. **框架层面 LangGraph 最契合**需求生成的 HITL/审计/回放诉求，但框架差异远小于架构差异；
6. **业界最佳实践收敛于同一路径**：先澄清（Discovery-first / 每次一问 / HARD-GATE）→ Schema 化生成 → 脚本校验 → 场景化模板变体。
