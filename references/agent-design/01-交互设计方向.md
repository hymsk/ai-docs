## 1. 背景与问题定义

### 1.1 为什么文档生成需要 Agent

- 开发者约 **30% 的时间**花在阅读和理解代码上（GitHub 开发者调查），其中大部分消耗在缺乏或过时文档的代码库中。
- 传统文档的核心困境不是"没人写"，而是**写完即过时**。人工维护 `AGENTS.md`、`CLAUDE.md` 等说明文件，在频繁提交的活跃仓库中几周内就会失效。
- LLM Agent 的成熟改变了这一点：API 参考可从类型自动生成，架构文档可由 AI 从代码推断，只有"决策记录（ADR）"等代码中不存在上下文的内容才需手写。

### 1.2 核心矛盾（也是交互设计的切入点）

| 矛盾 | 交互设计要回答的问题 |
| --- | --- |
| 自动化 vs 可控性 | 用户如何信任并干预一个自主写作的 Agent？ |
| 生成速度 vs 可验证性 | 长文输出时用户如何确认内容没有幻觉？ |
| 一次生成 vs 持续维护 | 更新文档时用户如何低成本审查增量变更？ |
| 机器可读 vs 人类可读 | 文档同时服务人类读者和 AI Agent 时结构如何取舍？ |

**结论**：文档生成 Agent 的成败，一半在生成质量（RAG、证据引用），另一半在**交互设计**——即"人如何观察、理解、纠正、信任 Agent 的产出"。

## 2. 文档生成 Agent 的典型架构

以 DeepWiki / OpenWiki / Litho (deepwiki-rs) 为代表的现代文档生成 Agent，普遍遵循一条确定性流水线：

```
扫描 Scan → 解析 Parse → 研究 Analyze → 生成 Generate → 校验 Verify → 格式化 Format → 导出 Export
```

关键组件：

| 组件 | 职责 | 交互关联 |
| --- | --- | --- |
| 预处理 Agent | 扫描目录结构、提取项目元数据 | 决定进度展示的粒度 |
| 研究编排器（Research Orchestrator） | 多个研究 Agent 并行分析架构/边界/工作流 | 中间产物可视化 = 透明度设计 |
| 记忆块（Memory Chunk） | 跨阶段共享状态，避免重复检索 | 支持断点续跑与增量更新 |
| ReAct 推理循环 | 迭代式"思考-行动-观察" | 思考链是否展示是重要 UX 抉择 |
| 编辑器 Agent 组 | Overview / 架构 / 流程 / 边界各由专职 Agent 撰写 | 分章节流式输出 |
| 校验层 | Mermaid 语法校验、完整性检查、自动修复（如 Mermaid Fixer） | 错误自动修复 vs 提示用户修复 |

**对交互设计的启示**：流水线的每个阶段都是潜在的"交互锚点"——进度反馈、中间产物预览、人工介入点的位置都应映射到这条链路上。

## 3. 交互设计理论基础

### 3.1 Microsoft HAX：18 条 Human-AI 交互准则（CHI 2019，获奖论文）

基于 20+ 年研究综合而成，经 49 名设计师 × 20 个 AI 产品验证。按四个交互阶段组织：

**初始阶段（Initially）**
1. 让用户清楚系统能做什么（设定准确预期）
2. 让用户知道系统做得有多好（能力边界）
3. 让系统在恰当时机感知上下文
4. 向用户展示系统能感知到的环境信息

**交互中（During Interaction）**
5. 减少社交暗示，避免过度拟人引发错误预期
6. 屏蔽与社会敏感话题相关的干扰
7. 支持高效消除歧义（disambiguation）
8. 支持高效修正（query correction）
9. 让服务可随时被否决/关闭

**出错时（When Wrong）**
10. 记住最近的交互并保持短期间一致性
11. 让用户知道"为什么系统这么做了"
12. 帮助用户记住全局（global awareness）
13. 鼓励用户给出细粒度反馈

**随时间演进（Over Time）**
14. 与用户的近期行为保持一致
15. 从用户行为中学习并个性化
16. 谨慎且有节制地更新模型（避免突变）
17. 鼓励用户在长期使用中给予反馈

配套工具链：HAX Workbook（优先级规划）、Design Library（模式库）、Playbook（失败场景推演）。

### 3.2 Google People + AI Guidebook（PAIR）

六大章节中的核心原则：
- **明确性（Clarity）**：让用户理解系统的能力与局限；
- **反馈与控制（Feedback & Control）**：设计反馈和控制机制来改进 AI 和体验；
- **错误管理**：诊断和管理 AI 错误及其使用情境；
- 新趋势 **Interaction Design Policies（交互设计策略）**：不只针对"任务"，而是为"机会（opportunity）"设计——AI 应在合适的时机主动提供超出任务本身的价值。

### 3.3 对文档生成场景的直接映射

| HAX 准则 | 在文档生成 Agent 中的落地 |
| --- | --- |
| #7 高效消歧义 | "你想要 API 参考还是架构总览？"以选项而非自由文本澄清 |
| #11 解释为什么 | 引用源码行号佐证每个论断（证据式写作） |
| #13/#17 细粒度反馈 | 对单段落点踩 → 反哺风格规则库 |
| #16 谨慎更新 | 增量更新走 PR 而非直接覆盖主分支 |

## 4. 六大核心 Agentic UX 交互模式

源自 Smashing Magazine《Designing For Agentic AI: Practical UX Patterns For Control, Consent, And Accountability》（2026-02），是当前最系统的 Agent 交互模式总结：

### 模式一：意图预览（Intent Preview）
- **适用**：不可逆或高影响动作（如覆盖已有文档、批量重写）。
- **做法**：Agent 动手前展示"我打算做什么 + 会改哪些文件"。
- **指标**：接受率 >85%；风险：用户感觉"被突袭"。

### 模式二：自主度旋钮（Autonomy Dial）
- **适用**：风险等级可变的任务。
- **分级示例（文档场景）**：
  - L0 建议：只给大纲，人写正文
  - L1 草稿：生成草稿，逐段确认
  - L2 协作：自动写入新文件，PR 审查后合并
  - L3 自主：定时任务自动更新文档并向主分支发 PR
- **指标**：设置变更频率（Setting Churn）；风险：功能整体被弃用。

### 模式三：可解释决策依据（Explainable Rationale）
- **适用**：后台或自主执行的任务。
- **心理机制**：解释让 Agent 的行为"有逻辑而非随机"，帮助用户建立正确心智模型。
- **好解释的特征**：① 有据可依（链接到源码/规则/用户偏好）；② 简单直接。
- **指标**："为什么？"类工单数量下降。

### 模式四：置信度信号（Confidence Signal）
- **适用**：专家级或高风险系统。
- **做法**：标注每段生成的置信度；低置信段落要求人工复核。
- **风险**：自动化偏见（automation bias）——用户盲目相信高置信标记。

### 模式五：操作审计与撤销（Action Audit & Undo）
- **适用**：几乎所有 Agentic 系统（基础模式）。
- **心理机制**：可恢复性创造心理安全感，用户才敢放权。
- **最佳实践**：时间线视图 + 清晰状态标识 + 有时限的撤销窗口（明确告知何时变为不可逆）。
- **指标**：回退率 <5%。

### 模式六：升级通道（Escalation Pathway）
- **适用**：用户意图模糊、信息不完整的场景。
- **三种形式**：请求澄清 / 给出选项 / 转交人类。
- **核心原则**：好的 Agent 不猜，而是升级求助。
- **健康指标**：求助频率 5–15%（太低=瞎猜，太高=无能）；升级后完成率 >90%。

### 汇总速查表

| 模式 | 最佳场景 | 主要风险 | 关键指标 |
| --- | --- | --- | --- |
| 意图预览 | 不可逆操作 | 用户被突袭 | 接受率 >85% |
| 自主度旋钮 | 风险可变任务 | 功能弃用 | 设置流失率 |
| 可解释依据 | 后台自主任务 | 被当成 Bug | "Why"工单量 |
| 置信度信号 | 专家/高风险 | 自动化偏见 | 审查差值 |
| 审计与撤销 | 所有系统 | 信任永久损失 | 回退率 <5% |
| 升级通道 | 意图模糊 | 灾难性自信猜测 | 恢复率 >90% |

## 5. 面向"文档生成"场景的交互设计策略

将上述通用模式具体化为文档生成 Agent 的十项策略：

### 5.1 大纲先行，分阶段生成（Progressive Disclosure）
先产出目录大纲供确认，再逐章生成。把"整篇推翻重来"的高成本纠错，拆解为"逐章微调"的低成本纠错。对应 HAX #7/#8。

### 5.2 证据式写作（Evidence-Based Generation）
- 每个论断附带**源码文件 + 行号引用**（deepwiki-skill 的核心卖点："每句话都有源代码行号佐证，告别胡编乱造"）。
- 交互上表现为：悬停/点击论断即可跳转源码。这是文档场景下最强的可信度设计。
- 无法找到证据的内容显式标注 `[待验证]` 而不是静默输出幻觉。

### 5.3 流式输出 + 结构化进度（Streaming & Progress）
- 长文档必须流式渲染，降低感知延迟。
- 按"研究 → 大纲 → 章节 → 图表"的阶段展示进度条，而非黑盒等待。
- 可选展示 Agent 的推理步骤摘要（透明度 vs 干扰度的权衡，默认折叠）。

### 5.4 Diff 驱动的增量更新（Diff-First Review）
- 更新场景永远以 **diff 视图**呈现，绝不静默覆盖。
- 参考 OpenWiki：更新通过 GitHub Action 定期执行，产出是 **Pull Request**，由人合并——文档变更天然进入评审队列。
- 结合 git diff 判断"哪些 commit 影响了哪些文档页"，只更新受影响部分。

### 5.5 人机分工契约（Human-in-the-Loop 分层）
| 内容类型 | 生成方式 | 理由 |
| --- | --- | --- |
| API 参考 | 类型系统全自动生成 | 机械映射，无需判断 |
| 架构文档 | Agent 生成 + 人审 | 价值密度最高，AI 已能胜任 |
| ADR / 业务上下文 | 纯人工 | 代码中不存在的信息 |

### 5.6 图表的生成-校验闭环
Mermaid 是文档 Agent 最常用的图表格式但极易出语法错。参考 Mermaid Fixer 模式：JS 沙箱内校验语法 → 失败自动调 LLM 修复 → 输出前后对比报告。用户看到的永远是已渲染成功的图。

### 5.7 双受众文档架构（Dual-Audience Structure）
文档同时服务人类与下游 AI Agent：
- 入口保持轻量（如 `quickstart.md` 作为导航地图），详细内容分层存放；
- 指令文件（`AGENTS.md`/`CLAUDE.md`）只放**引用指针**而非全文——Karpathy 的观点：结构化 wiki 优于把所有上下文塞进单个巨型文件；
- 为机器追加 `.md` 直链、llms.txt、sitemap.md 等 Agent 友好接口。

### 5.8 反馈的细粒度捕获
支持段落级的"采纳/修改/拒绝"三态反馈；拒绝时可选原因（事实错误/风格不符/遗漏）。这些数据用于迭代 prompt 规则库与 few-shot 示例，形成飞轮。

### 5.9 优雅降级（Graceful Degradation）
Agent 表现不佳时可一键回退传统流程（模板 + 手动编辑）。永远保留"不用 Agent"的出路，这本身是一种信任设计。

### 5.10 修复与道歉设计（Design for Repair）
Agent 写错了怎么办：清晰的更正入口、对错误的主动承认（"上一版第 3 节引用了已删除的函数，已修正如下"）、以及时间线上可见的自愈过程。

## 6. 工程落地要点

### 6.1 上下文管理
- 让 Agent 用搜索工具自己拉取上下文，不要手工堆砌文件路径；
- 项目根目录放置标准化说明文件（AGENTS.md），承载项目目标、约定、已知陷阱——减少幻觉与检索成本；
- 上下文是昂贵的：每个 token 都要过"租金"考核，技能/规则分层加载（始终加载的 Rules / 按需加载的 Skills / 深层 References）。

### 6.2 确定性流水线 + LLM 的混合编排（Litho 经验）
- 目录扫描、缓存、导出等环节用确定性代码，只在"理解与撰写"环节调用 LLM；
- 缓存 LLM 结果（CacheManager），支持跳过阶段（`--skip-preprocessing --skip-research`），降低重复生成成本；
- 并行子 Agent（Subagents）加速多章节生成。

### 6.3 CI/CD 集成
```
schedule/GitHub Action → openwiki --update
  → 读取自上次运行的 commits + git diff
  → 仅更新受影响的 wiki 页面
  → 自动开 Pull Request（不直接进 main）
  → 人在评审中合并
```
关键设计：**更新独立于任何编码会话运行**，不给开发工作流增加延迟。

### 6.4 安全与权限
- 说明性上下文（AGENTS.md）≠ 权限控制面；最小权限应落在工具自身的审批、沙箱、allowlist、hooks 上；
- 写文件类操作默认进入"意图预览 + 确认"通道。

## 7. 评估指标体系

### 7.1 文档质量指标
| 指标 | 定义 | 目标 |
| --- | --- | --- |
| 事实准确率 | 论断可被源码/证据验证的比例 | >95%，未验证内容占比 <5% |
| 新鲜度 | 最后一次文档更新落后于代码变更的天数 | <7 天 |
| 引用覆盖率 | 含源码引用的段落数 / 总段落数 | 监控并持续提升 |
| 图表可用率 | 渲染成功且语义正确的图表比例 | >98% |

### 7.2 交互体验指标（交互设计方向的独有视角）
| 指标 | 说明 |
| --- | --- |
| 首次接受率 | 生成的初稿未经重大修改被采用的比例 |
| 每千字人工干预次数 | 衡量自动化程度；理想趋势：下降 |
| 审查耗时 | diff 评审平均时长（过长说明 diff 太粗） |
| 升级求助率 | 5–15% 健康；升级后恢复成功率 >90% |
| 撤销/回退率 | <5%；升高说明前置预览失效 |
| 信任代理曲线 | 使用 Undo 后 7 天内升级到更高自主档位的用户比例 |

### 7.3 业务结果指标
新人入职周期缩短幅度、"文档找不到答案"类提问下降率、下游 Agent 因上下文改善带来的返工率下降。

## 9. 反模式与常见失败模式

| 反模式 | 表现 | 后果 | 解法 |
| --- | --- | --- | --- |
| 黑盒长生成 | 点一下按钮等 5 分钟出全文 | 用户无法中途纠偏，信任崩塌 | 分阶段 + 流式 + 大纲先行 |
| 静默覆盖 | 直接改写现有文档不留痕 | 用户失去掌控感 | 一切更新走 diff/PR |
| 无证据幻觉 | 论断无法追溯到源码 | 文档比没文档更危险 | 证据式写作 + 待验证标注 |
| 过度拟人 | "我认为这段代码很优雅" | 引发错误预期（HAX #5） | 克制社交话术 |
| 全自动一刀切 | 只有全手动/全自动两档 | 要么累死要么失控 | 自主度旋钮分级 |
| 该问不问 | 信息不足时自信瞎猜 | 灾难性错误 | Escalation Pathway |
| 单一巨型上下文文件 | 把几百页塞进 AGENTS.md | 浪费 token 且难维护 | 指针 + 结构化 wiki |
| 一次性交付 | 生成完就结束，无更新机制 | 两周后全部过时 | CI 定时增量更新 |

## 10. 设计检查清单（Checklist）

### 生成前
- [ ] 是否先呈现大纲/计划并获得确认？（Intent Preview）
- [ ] 是否声明本次任务的自主级别？（Autonomy Dial）
- [ ] 信息不足时是否有澄清提问而非猜测？（Escalation）

### 生成中
- [ ] 是否流式输出并显示阶段进度？
- [ ] 中间产物（研究结果、大纲）是否可视、可中断？
- [ ] 每个关键论断是否携带可跳转的证据引用？

### 生成后
- [ ] 是否提供 diff 视图而非直接覆盖？
- [ ] 是否有操作审计日志与撤销能力？（Audit & Undo）
- [ ] 低置信内容是否显式标记请求复核？（Confidence Signal）
- [ ] 图表是否经过语法校验/自动修复后才呈现？

### 长期运维
- [ ] 是否接入 CI 定时增量更新并以 PR 形式交付？
- [ ] 是否收集段落级细粒度反馈并回流到规则/prompt？
- [ ] 文档结构是否同时服务人类读者与下游 Agent（双受众）？
- [ ] 是否保留了优雅降级的手动路径？

# 深度篇（第二轮调研）

## 11. 人机协同写作的实证研究（CHI 2025–2026）

通用 UX 准则之外，HCI 学术界近两年针对"人与 LLM 共同写作"产出了直接可用的实证结论。

### 11.1 五种"使用中设计"风格与 14 种实践（CHI '25）

Monge Roffarello 等人对 19 名科研人员进行了真实写作任务的远程观察，发现用户并非被动接受工具设计，而是主动"改造"写作助手，形成五种 **design-in-use 风格**：

| 风格 | 含义 | 典型实践 | 对文档 Agent 的启示 |
| --- | --- | --- | --- |
| Teaching（教导） | 主动向 LLM 输入领域知识 | (Re)aligning / Generating / Refining / Implicit teaching；如先上传 PDF 给 Claude 建立上下文再开始写 | 必须提供"喂上下文"的正式入口（风格样例、术语表、项目背景），而非让用户在对话框里临时口述 |
| Resisting（抵制） | 刻意降低个性化以保真实性与可靠性 | Less personalization / Text resistance / Validating | 提供"不学习我的数据"开关；个性化要可关闭 |
| Repurposing（挪用） | 把助手用于非预期用途 | 拿 ChatGPT 起草、拿 Grammarly 校对的流水线组合 | 不要假设单一工具闭环；支持与既有工具链互操作 |
| Orchestrating（编排） | 自建管道串联多个工具 | 有参与者自己写了 VS Code 插件统一调用 GPT API | 内置"多步工作流"编排能力，减少用户自建 |
| Complying（顺从） | 接受默认设置照单全收 | — | 默认值即产品价值观：默认提示词/温度/风格必须精心设计 |

### 11.2 关键痛点：工作流断裂（Workflow Disruptions）

- 频繁在浏览器标签页和多个工具间切换会**碎片化写作过程**（8/19 参与者）。
- 设计含义：文档生成 Agent 应尽量**内联于用户已有的编辑环境**（IDE、Git 平台、docs 编辑器），而不是强迫用户切换到独立聊天窗口。

### 11.3 作者权漂移（Authorship Drift, CHI 2026）

最新研究追踪了人-LLM 协作写作中**自我效能感（self-efficacy）与信任如何随时间演化**：长期协作中作者对文本的"所有权感"会逐渐漂移。对文档场景的含义：

- 文档是团队的"作品"，Agent 大量代笔可能削弱工程师对文档的责任感和维护意愿；
- 对策：保留作者署名与贡献可视化（AI 生成段落标注来源）、让作者做最终的风格定稿决策——维持"人是作者，AI 是助手"的心理框架。

### 11.4 用户对 AI 文本的态度基线

同一研究线反复观察到：成熟用户会**批判性地审读 AI 生成文本**，并确保内容经过自己的审查与改写。这意味着文档 Agent 的产出界面必须为"逐段审读"优化，而不是鼓励"一键采纳"。

## 12. 信任校准：比"可解释"更进一步

### 12.1 核心发现："任何解释都比没解释好"是错的

Berkeley 的信任校准研究给出反直觉证据：**解释界面可能把人往错误方向推（nudge in the wrong direction），反而损害信任校准**。解释的价值取决于用户的情境理解，而非解释本身的存在。Zhang et al.（FAccT 2020）同样表明：置信度 + 解释的组合对准确率和信任校准的影响是非单调的。

### 12.2 UFES：可解释摘要的不确定性框架

Armstrong 等（Visible Language, 2025）提出 **Uncertainty Framework for Explainable Summaries (UFES)** 及多智能体验证系统（MAVS）的 10 项界面特征，并给出 8 种开源的不确定性可视化方案。其五条信任校准原则（TC1–TC5）可直接迁移到文档生成：

| 原则 | 在文档生成 Agent 中的落地 |
| --- | --- |
| TC1 透明性（Transparency） | 展示"这段话基于哪次检索/哪个源文件"，而非只给结论 |
| TC3 支持人类决策过程的可视化 | 不确定性用渐进视觉编码（如下划线密度/色阶）标注低置信论断，而非弹窗打断 |
| TC4 交互性（Interactivity） | 用户可通过显式操作影响结果：点选某段要求"补充证据"或"重写" |
| TC5 虚拟代理（Virtual Agents） | 多角色分工（研究者 Agent、撰写 Agent、审校 Agent）分别可见、可问责 |

### 12.3 信任校准 ≠ 信任最大化

目标是**校准**：该信时信、该疑时疑。过度设计"让人放心"的 UI（如满屏绿色对勾）会导致自动化偏见——用户不再审读，幻觉长驱直入。文档 Agent 的置信度展示应敢于示弱。

## 13. 可中断性：长任务中的用户干预设计

### 13.1 InterruptBench：首个系统性研究（arXiv 2604.00892, 2026-04）

随着 Agent 从短任务走向数小时的长任务，**用户中途改变主意**成为常态需求。该研究首次系统评估长周期、有环境约束下的可中断 Agent，形式化了三种真实中断类型：

| 中断类型 | 场景示例（映射到文档生成） |
| --- | --- |
| Addition（追加） | "生成时顺便把每个 API 都加上错误码表格" |
| Revision（修正） | "不对，这个模块叫 X 不叫 Y，重新检索一下" |
| Retraction（撤回） | "刚才说的英文版不用生成了" |

核心结论：
- 即使是最强的大规模 LLM，**有效且高效地处理中断依然困难**；
- 中断的处理效率影响高度依赖模型与场景，存在交互长度与生成成本的权衡；
- 多轮连续中断比单轮更难；
- 中断有时反而能纠正 baseline 失败（负的平均动作增量）。

### 13.2 对文档生成 Agent 的交互设计要求

1. **随时可中断且可续跑**：中断后基于已完成的中间产物继续（Litho 的 Memory Chunk 设计正是为此准备），而非从头再来。
2. **意图变更的三种语义**：产品层面应明确区分"追加/修正/撤回"并正确合并进任务状态，避免把撤回当新增处理。
3. **部分结果可检视**：长任务执行中允许查看已生成的章节——InterruptBench 强调"用户天然想检查部分结果、纠正看到的错误"。
4. **进度感知的中断点选择**：研究采用"相对进度注入中断"的评测法，提示我们中断恢复成本与任务完成比例相关，UI 应展示当前完成度百分比以帮助用户判断干预时机。
5. 相关基准可关注：UserBench（以用户为中心的交互式 Agent 评测）、*One Interaction Is Worth a Thousand Guesses*（深研型 Agent 的交互能力基准）——交互式 Agent 评测正在成为独立研究方向。

## 14. Agent 原生文档标准与"发现栈"

第二轮调研确认了一个结构性变化：**文档的第一读者已经不只是人**。

### 14.1 流量结构逆转

GitBook 2026 年 4 月的流量研究显示：在其托管的文档站点上，**AI Agent 占有意文档阅读量的 51.8%，首次超过人类读者**。这从根本上改变了文档的交互设计目标函数。

### 14.2 两类读者的稀缺资源错位（Jamdesk 总结）

> 人类的稀缺资源是**注意力（attention）**；Agent 的稀缺资源是**上下文 token（context tokens）**。

由此推导出四条 Agent 优先的文档写作原则：
1. **Write everything down**：Agent 读一切，显式优于简洁（与人类文档"尊重读者时间"的原则相反）；
2. **Make every page stand alone**：每页自包含，因为 Agent 是 fetch 单页而非浏览导航；
3. **Serve markdown instead of chrome**：直接返回干净 Markdown，剥掉导航/广告/JS 外壳；
4. **Treat error messages as first-class content**：精确的错误信息优于宽容的默认行为。

### 14.3 发现栈（Discovery Stack）三层架构

| 层 | 标准/协议 | 作用 | 现状与争议 |
| --- | --- | --- | --- |
| 索引层 | `llms.txt` v2 | 站点根目录的 Markdown 索引：是什么、在哪、一句话描述 | 采用量一年增长 8.8 倍（2026-05 达 36,120 站）；**但 Ahrefs 实测 97% 的文件一个月内收到零次 AI 请求**，Google John Mueller 将其比作 keywords meta 标签——标准本身存在争议 |
| 内容层 | `.md` 直链（`page.md` / `page.html.md`）、`rel="alternate" type="text/markdown"`、`rel="describedby"` | 任意页面的干净 Markdown 版本 | 已被 Mintlify / GitBook / Fern 等平台自动生成 |
| 查询层 | MCP Server | 让 Agent 用自然语言查询文档，而非爬取页面 | GitBook 2026-02 上线 MCP 分析：能看到开发者经 Claude Code/Cursor 提的真实问题——这是站点外流量首次变得可观测 |

### 14.4 AGENTS.md 开放标准

- 定位："给 Agent 看的 README"，存放项目指令、约定、约束的**唯一可预测位置**；
- 支持**目录级分层**：子目录的 AGENTS.md 在 Agent 读取该目录文件时动态加载（以 system-reminder 注入），适合 monorepo；
- 关键工程细节（Kilo Code 实践）：AGENTS.md 属于指令层，应设为**写保护文件**；权限控制仍应落在审批/沙箱等真实控制面。

### 14.5 对"生成文档的 Agent"的直接要求

生成的文档应**原生符合上述三层标准**：自动产出 `llms.txt` 索引、每页附 Markdown 直链、可选暴露 MCP 查询接口。GitBook 与 Mintlify 均已提供 agent-readiness 评分工具（Agent Score），可作为生成质量的验收器。

## 15. 商业平台竞品格局：文档产品的 Agent 化

### 15.1 主要玩家对比（2026 年中）

| 平台 | 定位 | Agent 相关交互功能 | 短板 |
| --- | --- | --- | --- |
| **Mintlify** | "The Knowledge Platform Built for Agents" | Agent Score（检测 Agent 能否读懂你的文档）；Mintlify Index（2026-08：聚合 9000 个文档站为编码 Agent 提供自然语言检索层）；站内 AI 助手；Automations（代码变更后自动更新文档、翻译） | 结构改动需改代码；积分制计费不可预测（Pro $450/月 + AI 积分：一次助手回复约 23 credits，一次 agent 运行约 110–115，一次翻译 automation 最高 913） |
| **GitBook** | 企业级混合团队文档 | GitBook Agent（主动从 GitHub/Linear 发现内容缺口并发起 change request）；MCP 分析（看到站点外的 Agent 查询问题）；可嵌入任意产品的 AI 助手；AI Insights 把站内提问聚类成内容缺口报告 | AI 偏创建而非维护——文档不会自动感知产品变化；按站点+席位计费 |
| **ReadMe** | API 参考为中心 | Agent Owlbert（2025-10）：文档 linting、风格强制、对话式搜索 | 散文类内容（onboarding/wiki）体验差 |
| **DeepWiki / OpenWiki / Litho** | 开源仓库 wiki 生成 | 见第一轮第 8 章 | 面向代码库，非产品文档平台 |

### 15.2 行业共识与共同盲区

- **共识**：Agent 流量分析已成为标配功能；llms.txt/.md/MCP 三件套成为发布基线；"内容缺口检测 → 自动发起更新请求"是下一代主打方向（GitBook Agent 已落地）。
- **共同盲区**：几乎所有平台仍是 **creation-focused 而非 maintenance-focused**——没有平台能让文档自动感知被文档对象的变化并自主保持新鲜（Ferndesk 评测原话）。这正是文档生成 Agent 创业/立项的最大机会窗口。
- **定价信号**：Mintlify 的用量积分制 vs GitBook 的包月制的竞争说明——**Agent 化功能的成本模型本身就是产品设计的一部分**（用户对"每次生成花多少钱"的感知会影响其使用频率与信任）。

## 16. 第二轮结论：对设计策略的修订与增补

综合两轮调研，对第 5 章策略清单做如下修订与增补：

### 修订
- **5.7 双受众文档架构 → 升级为"双资源模型"**：为人类优化注意力（渐进披露、导航、搜索），为 Agent 优化 token（自包含页面、干净 Markdown、显式信息）。两者不是权衡而是并存的两套视图。
- **5.10 修复与道歉设计**：补充作者权保护——AI 代笔需标注来源，维护人类作者的最终署名权，防止 Authorship Drift 侵蚀维护意愿。

### 增补策略

**S11. 三种中断语义的一等公民化**
将 Addition / Revision / Retraction 作为任务状态机的显式操作建模，中断后从记忆块续跑而非重启。（依据：InterruptBench 2026）

**S12. 校准式透明，而非安抚式透明**
置信度和解释的呈现必须接受"校准测试"：低质量内容要敢于示弱；警惕解释本身误导用户。（依据：UFES、Berkeley 信任校准研究）

**S13. 喂上下文的正式入口**
提供风格样例、术语表、历史文档等结构化上下文注入机制，替代聊天框里的口头教学。（依据：CHI '25 design-in-use 研究）

**S14. 个性化可关**
尊重 Resisting 型用户：提供"不学习我的数据""不做个性化"的显式开关。

**S15. 内联于现有工作流**
Agent 入口放进 IDE / Git 平台 / docs 编辑器，避免独立的聊天孤岛造成工作流断裂。

**S16. 生成结果原生通过 Agent-readiness 检验**
把 llms.txt、`.md` 直链、每页自包含、显式错误信息作为文档生成的输出规范，并用 Agent Score 类工具做回归验收。

**S17. 成本可见性**
Agent 化功能（生成/翻译/自动化更新）向用户明示预估消耗（token 或费用），防止"用量焦虑"反向抑制使用。
